# GBServer 2.0.0 迭代路线图

> 状态：建议执行顺序。基线为 `v2.0` 分支 `6de11db`（2026-10-17）。
> 本文定义版本范围和验收证据；具体实现以每项设计、代码与测试结果为准。

## 版本目标

让设备接入、点播、录像和控制操作形成**可确认结果、可定位故障、可重复验收**的闭环。保留当前分工：浏览器业务 HTTP 请求进入 GBServer；GBServer 调用 ZLM 管理接口获取流状态并控制流；浏览器使用 GBServer 返回的地址直接访问 ZLM 媒体流（FLV/HLS/WS/WebRTC）。录像下载与缩略图继续由 GBServer 提供。`/zlm/{media_server_id}/{path}` 是受鉴权保护的管理代理，不作为浏览器媒体流入口。

当前后端、前端包版本与 SIP `User-Agent` 已统一为 `2.0.0`，开发环境绝对 `/api` 路径已代理到后端（`6de11db`）。这只确认代码与构建，不代表 2.0 功能已验收。

## 实施顺序

### M0：建立可复现基线

**任务**

- 在 `v2.0` 上记录后端单测、前端构建、关键 E2E 的实际结果及所用数据库、ZLM、设备或 Mock；只把本轮结果写进 `STATUS.md`。
- 核对 `OPEN_ISSUES.md` 与路由表的差异。C9 所称“收藏删除 GET 必然 405”与当前已注册的 GET handler 不一致，须用路由测试或实际请求确认后修正文档。
- 检查开发与生产环境的业务 API、缩略图、日志导出、录像下载均到 GBServer；检查 ZLM 的流地址和 WebRTC ICE 在目标部署拓扑下可达。

**完成条件**：有可复现的环境与命令记录；每个结论标明静态检查、自动化测试、实际运行三类证据中的哪几类已具备。基线失败先登记，不把历史通过数当作当前通过。

### M1：媒体与录像可靠性（首个功能迭代）

**任务**

- 修正 B1：普通点播已经等到 ZLM 媒体就绪时，不再因设备 SDP 端口与 ZLM RTP 端口不同触发无效 `connectRtpServer`；TCP-PASSIVE 保留必需的主动连接，失败时精确清理 RTP Server 和 `StreamType::Play` 会话。
- 为录像计划启动重试补定向测试：仅流尚未出现时在固定预算内重试；不可恢复错误立即失败；“已在录制”保持幂等。
- 重写 `cloudRecord` E2E 的成功判据：只接受本次计划产生的新录像文件及数据库记录，不把历史录像、HTTP 200 或固定短等待当作成功。
- 运行中监测后端、ZLM 和 Mock 的存活；依赖进程退出时报环境故障并保留诊断信息。

**完成条件**：定向 Rust 测试、`cloudRecord` E2E 和目标 ZLM 运行场景通过；能证明 SDP 端口不一致但媒体已就绪时播放不中断，也能证明本轮新 MP4 落库。详细设计见 `superpowers/specs/2026-09-19-media-recording-reliability-design.md`；现有未跟踪实施计划须先按当前代码复核，再用于执行。

### M2：设备命令结果闭环

**任务**

- 修正 B14：解析 `DeviceControl`、`ConfigDownload` 等设备 MESSAGE 应答，按设备、命令类型及 SN/请求上下文匹配待处理操作；区分 SIP 传输成功、设备执行成功、设备拒绝和超时。
- 给控制与配置页面返回可信结果；无法确认执行时明确显示“未确认”，不把发送成功表述为设备已执行。
- 复核 C8 的 `hasAudio` 来源，以真实流媒体信息和设备目录字段的语义划清边界；修正明显错误的前端展示。

**完成条件**：应答成功、失败、重复、迟到和超时有自动化覆盖；至少一台真实 GB28181 设备验证控制或配置命令的请求与结果闭环。真机未覆盖的命令单列为“未验证”。

### M3：受控运维能力

**任务**

- 完成 A2：管理员可读取有界、脱敏的最近 ZLM Hook 摘要与 Redis/StateStore 连通性诊断；所有新管理端点调用 `authz::require_admin`。
- 让媒体节点、流状态、录像故障能从 GBServer 的接口、日志或页面定位到具体节点与流；不向浏览器暴露 ZLM secret、Redis 密码或完整 Hook 载荷。
- 将 API Key 管理界面作为本阶段候选：后端接口已存在，只有确认实际管理使用场景后才加入 2.0.0 必交付范围。

**完成条件**：管理员、普通用户、未登录三类权限结果经过测试；ZLM/Redis 不可用时返回可诊断且不泄密的结果；真实故障演练能定位原因。

### M4：集成验收与发布门禁

**任务**

- 在真实 GB28181 设备上复验注册/注销、目录同步、点播与停止、回放、录像、命令应答，以及分页目录、主动 BYE、心跳超时等边界场景。
- 覆盖 SQLite、PostgreSQL、MySQL 的改动相关路径；运行后端测试、前端构建、关键 Playwright 用例和生产部署冒烟。
- 用本轮证据更新 `STATUS.md` 与 `OPEN_ISSUES.md`，明确哪些功能只有 Mock 证据、哪些已有真机证据；核对对外版本显示均为 `2.0.0`。

**完成条件**：核心 GB28181 直播、录像、控制闭环有静态、自动化和真实运行三层证据；阻断性缺陷关闭，剩余限制在发布说明中逐项列明。是否打标签与发布另行决定。

## 条件性工作与本版范围外

- **JT1078 真终端（C3、D2）与真实对讲互通（D3）**：设备可用时纳入专项联调，修正固定注册鉴权码、`0x0102` 语义及音频问题；若没有真终端/音频设备，本版不能宣称这些能力已通过真实设备验收，也不以 Mock 通过替代。
- **SY 定制接口（A1）**：只有取得对接方的请求/响应契约与验收样例后才排入 2.0.0；现有等价能力应复用，不盲目新增别名。
- **外部签名协议 `/api/v1/*`（A3）**：保持范围外；它需要独立鉴权与契约设计。
- **大规模代码债清理（C1/C2）**：仅在直接阻碍本路线图任务时顺带处理，不作为发布门禁。

## 工作项规则

每个功能项先写明接口/协议契约和失败语义，再实施与定向测试；涉及设备、ZLM、数据库或浏览器的行为，以相应真实运行记录作为最终证据。新管理接口统一使用 `ApiResult<T>`、`authz::require_admin` 与现有 OpenAPI 路由注册方式。更新状态时区分“代码已写”“测试通过”“目标环境已验证”。
